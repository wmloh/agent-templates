# Initialize project instructions

Use this file to initialize repository instructions for a new or existing project. Produce a concise root `AGENTS.md`, modular workflow files under `workflows/`, and a compact root `PROJECT_MAP.yaml` for tracking by the main project repository. Always include `workflows/UPDATE_WORKFLOW.md`; the other six workflows are user-selected. This file is the initialization procedure; do not copy the entire procedure into `AGENTS.md`. Subsequent template updates use the generated update workflow only when the user explicitly requests them.

After initialization is entirely complete and checked, move the supplied `INIT_AGENT.md` to `workflows/INIT_AGENT.md` instead of deleting it. If the template was supplied only in conversation, save its exact supplied contents there. This is the unmodified baseline for future comparisons, eligible for tracking in workflow Git. Keep ongoing rules in `AGENTS.md` and the linked workflow files; the saved template is a version record, not instructions to rerun initialization. Never edit it to reflect project customizations. Replace an established baseline only after a successful update through `UPDATE_WORKFLOW.md`.

Assume the `probe-me` and `decision` skills are available. Read their actual instructions when using them; do not invent their interfaces.

## 1. Inspect before interviewing

- Read existing applicable `AGENTS.md` files and relevant instruction files. Inspect a small amount of repository structure, manifests, entry points, and documentation to ground the interview. For an empty repository, establish the intended structure through questions.
- Stay within the repository unless the user explicitly authorizes access elsewhere. Access to an externally stored skill must also follow applicable access rules; ask for access or its supplied contents if necessary.
- Preserve user changes and project-specific instructions. Do not overwrite artifacts, install packages, download dependencies, change environments, or run expensive workloads during initialization.
- Treat existing instructions as evidence of intent. Merge compatible rules. Surface conflicts with a proposed resolution and ask when intent remains unclear; do not silently replace local policies with these defaults.

## 2. Interview with probe-me

Invoke `probe-me` before editing. Ask the user at least **six distinct, relevant questions**, in manageable rounds of two or three questions. Prefer the multiple-choice interface with concrete trade-offs and a free-text alternative. If that interface is unavailable, ask numbered questions in conversation. Use only parameters the available tool supports.

Always ask about **project domain** and **execution environment**, even if repository evidence suggests the answers. For other topics, use inspected evidence to offer informed choices rather than making the user repeat documentation. Cover all six topics below; follow up on consequential gaps or conflicts.

1. **Domain and outcome:** What does this project do, who uses its outputs, and what constitutes success? Offer relevant choices such as ML research, ML applications, general Python software, or another domain. Do not impose ML research standards on unrelated projects.
2. **Environment:** Where will work run: WSL 2, native Linux, macOS, Windows, a container, a remote cluster, or another environment? Establish the relevant local/remote distinction, environment manager, and any hardware constraints. Ask explicitly whether WSL 2 applies.
3. **Language and testing:** Confirm languages, framework/tooling conventions, acceptable lightweight checks, and test time and compute budgets. Tests, including files under `tests/`, are allowed; confirm that suites should stay concise and meaningful as development continues. Confirm the default restriction against subdirectory `README.md` files unless explicitly requested. Adapt Python-specific style rules only where relevant.
4. **Workflows:** Explain that the update workflow is always included and runs only on explicit request. Ask which other workflows the user wants: code, task tracking, review, paper writing, memory, or reusable agent tools. Create the update workflow and only the selected optional workflow files; every workflow present is active according to its routing trigger. For an existing setup, confirm which workflows to retain or add; do not delete existing files merely because they were not selected. The new-chat memory listing remains required even if the memory workflow is not selected or no notes exist. Identify any additional workflow that needs its own file.
5. **Execution and artifacts:** Which commands, resource budgets, and artifact locations matter? Establish whether training, evaluation, data processing, network access, or other substantial runs are authorized. Preserve the explicit restrictions on installations, environment changes, destructive commands, and artifact overwrites unless the user revises them.
6. **Collaboration and decisions:** How should tasks, unresolved decisions, and user requests be tracked? Confirm the task and paper conventions below, the review audience, and whether any existing policy needs reconciliation. Distinguish human-initiated permanent decisions from agent-maintained fluid memory, and human documentation from agent resume notes. Confirm the compact project map and its feature-change maintenance rule. Establish whether a separate workflow Git repository and remote already exist, which remote and branch to use for cross-device synchronization, and whether network synchronization is authorized. Decisions, memory, and reusable agent tools belong in that nested repository, excluded from the main project; the user handles staging and commits. Do not invent a remote or treat local Git initialization as completed synchronization.

Challenge proposals constructively where evidence reveals a practical problem. Keep the interview relevant to the project's domain; add scientific, deployment, or evaluation policies only when the user requests or confirms them.

Summarize decisions, remaining assumptions, and consequences before editing. If the interview receives no response, leave initialization unfinished and resume the unanswered questions on continuation, subject to the available tool's governing instructions. For an individually skipped optional detail, state a conservative assumption. Never treat silence as authorization for restricted actions.

## 3. Generate or merge the files

State the intended edits first. Keep `AGENTS.md` and `PROJECT_MAP.yaml` at the project root. The map is the only generated workflow item intended for tracking by the main project repository. Create or update `workflows/UPDATE_WORKFLOW.md`, the selected optional `workflows/*_WORKFLOW.md` files and, only when needed for the corresponding workflow, `workflows/TASKS.md`, `workflows/REQUESTS.md`, `workflows/memory/`, or `workflows/tools/` with `TOOL_MAP.json`. Retain the supplied template at `workflows/INIT_AGENT.md` after the final checks. The `workflows/decisions/` store follows the decision skill; only an explicit decision `make` request initializes it. Keep these support files eligible for tracking in the nested workflow repository; leave staging and commits to the user. Additional personal workflow files also belong there. Use Markdown links relative to the file containing the link: root `AGENTS.md` links into `workflows/`, while files inside `workflows/` link to siblings or use `../` for project files. All paths below are relative to the project root unless explicitly stated otherwise. Preserve unrelated content and edits.

When transferring applicable ongoing rules into `AGENTS.md` and `*_WORKFLOW.md` files, copy each sentence exactly when the rule needs no project-specific or environment-specific modification. Do not paraphrase, condense, or expand an unchanged rule. If a rule needs adaptation to confirmed project or environment requirements, existing instructions, selected workflows, or relative link locations, reword the whole affected rule as needed while preserving its intended meaning and any applicable constraints. Keep other applicable rules verbatim. This applies to ongoing rules, not initialization procedure, examples, or unselected workflows; preserve existing local instructions and resolve conflicts as directed above.

### AGENTS.md: shared operating rules and routing

Keep this file lean. Include a short project description, confirmed environment facts, the shared rules below, and the routing table. Put workflow-specific detail in the linked files. Adapt workflow-specific bullets and links to the workflows actually present; do not link to missing files or discard shared safety, storage, or documentation rules. Record durable decisions, not the interview transcript.

Preserve these core rules:

- Do not read, search, or modify files outside this repository unless the user explicitly asks. An explicit template-update request authorizes fetching the public template source specified in `workflows/UPDATE_WORKFLOW.md`. An explicit request to update named skills also authorizes fetching their specified public sources and inspecting and updating their confirmed installation paths, including outside this repository, through that workflow's review and approval process. It does not authorize changes to other skills or environment settings.
- Before editing files, state the intended edits.
- Preserve changes from the user and other agents. Do not revert, overwrite, or clean up unrelated files unless explicitly asked.
- Do not stage or commit any files in any repository, including project files and workflow files. This applies during initialization and ongoing work; leave staging and commits to the user.
- Do not run destructive commands such as `rm`, `git reset`, `git checkout`, broad `mv`, or cleanup scripts unless the user explicitly approves the exact action. Workflow exceptions are narrowly scoped removal of obsolete notes under `workflows/memory/` through `workflows/MEMORY_WORKFLOW.md`, and trimming redundant or obsolete tests through `workflows/CODE_WORKFLOW.md`; neither authorizes broad cleanup.
- Do not install packages, download dependencies, or change environments unless explicitly asked. Notify the user of missing environment components or packages before proceeding with dependent work.
- Lightweight read-only inspection and small, relevant syntax/import checks are acceptable when they do not touch large data or model artifacts. Follow confirmed project limits for other execution.
- For substantial features or experimental changes whose intended behavior is unclear, ask clarifying questions before editing and use `probe-me` as appropriate. Always honor an explicit invocation of that skill. Prefer multiple-choice questions and challenge proposals constructively.
- Do not overwrite result files, checkpoints, Parquet data, experiment caches, or plots. Use new output locations for authorized runs.
- At the start of every new chat, run `ls workflows/memory` from the project root. A missing directory means no memory exists; do not create it merely for this check. Report other listing failures rather than assuming there are no notes. Use descriptive filenames to identify notes relevant to the requested task, then read `workflows/MEMORY_WORKFLOW.md` and those notes when relevant. If relevant notes exist but that workflow is absent, ask whether to add it before using the memory workflow. Do not repeat the mandatory listing for each turn, continuation, or context compaction within the same chat.
- Read workflow files only when their triggers apply. Open their explicit paths because parent Git listings and ignore-aware searches may omit `workflows/`. For a task spanning workflows, read each applicable file; do not load all files merely because they are linked. The explicit update process is an exception: read all existing workflow instruction files to reconcile shared rules and project customizations. Keep `workflows/INIT_AGENT.md` as an unmodified comparison baseline; it is not an active workflow.
- Keep agent-initiated working choices and resume context in `workflows/memory/` through [MEMORY_WORKFLOW.md](workflows/MEMORY_WORKFLOW.md). Memory is fluid; human-initiated instructions in `workflows/decisions/` persist until the user changes them. Memory must not override those instructions or become permanent policy without an explicit decision request. Keep `docs/` and other established documentation locations focused on human understanding: accurate, readable explanations of the project's ideas and usage, rather than exhaustive implementation or process details. Put transient agent notes in memory, never in `docs/`, task descriptions, or unsolicited documents elsewhere.
- Keep `AGENTS.md` and `workflows/` locally excluded from the parent project Git repository. Workflow files, ledgers, requests, memory, decisions, and reusable agent tools belong in the separate workflow Git repository. Do not exclude decisions from workflow Git or create a further repository just for them. Run project Git commands from the project root and workflow Git commands with `git -C workflows ...` from that root; verify the repository boundary before Git operations.
- `workflows/TASKS.md` may contain only `# History` with historical bullets and `# Current` with checklists, plus blank lines. Do not add paragraphs or development notes, including at the start of `Current`. Follow [TASK_WORKFLOW.md](workflows/TASK_WORKFLOW.md) whenever editing the ledger.
- Use task IDs only in `workflows/TASKS.md` and files under `workflows/memory/`, not in other files or communications. Refer to tasks by descriptive names elsewhere. Task IDs may change when historical tasks are removed or compressed in `workflows/TASKS.md`; keep affected memory references current.
- The project map is in root [PROJECT_MAP.yaml](PROJECT_MAP.yaml), tracked by the main project repository rather than workflow Git. Consult it when locating work or understanding repository structure. Keep it very high-level and concise, with directory-relative nesting and brief descriptions on the same line as their path keys. Use two-space indentation, never tabs, and no multiline scalars (including `>-`). Group related files or summarize whole directories; it need not describe every file. Exclude all `AGENTS.md` and `README.md` files, all workflow or instruction files, everything under `workflows/`, and the map itself. Update it in the same change when a feature is added or removed; also correct affected entries when features or entry points move.

Include a routing table of this form with rows only for workflow files actually present. This table is the single location for workflow read triggers:

| File | Read when |
| --- | --- |
| [CODE_WORKFLOW.md](workflows/CODE_WORKFLOW.md) | Implementing, modifying, debugging, or testing code. |
| [TASK_WORKFLOW.md](workflows/TASK_WORKFLOW.md) | The user explicitly asks to create, track, or complete a task, condense completed current tasks, or compress historical tasks. |
| [REVIEW_WORKFLOW.md](workflows/REVIEW_WORKFLOW.md) | Reviewing code, designs, experiments, or written work. |

Do not add routing entries for missing workflows. If a later request needs a missing workflow, ask whether to add it, then create the agreed file and its routing entry. Preserve existing workflow files unless removal is explicitly authorized; every retained workflow remains active and routed. Link `PROJECT_MAP.yaml` separately as a navigation resource, not as mandatory reading for every task.

### Workflow file structure

Always generate `UPDATE_WORKFLOW.md`. Ask the user which of the other six workflow files they want, then generate only those selected. Every workflow file present is active according to its routing trigger. Keep each file focused on concise actionable rules; do not add status labels such as "Status: Active, on demand" or repeat read triggers such as "Trigger: ...". Read triggers belong only in the `AGENTS.md` routing table. Do not invent tools, paths, commands, or domain requirements. Do not duplicate shared operating rules or require reading unrelated workflows, except for the update workflow's explicit reconciliation step.

**workflows/CODE_WORKFLOW.md**

- Follow nearby code style and the confirmed language conventions. For Python, use Google-style docstrings for public functions/classes and nontrivial private helpers. Keep comments concise and focused on non-obvious logic.
- Avoid routine logging or printing in library functions. Warnings are acceptable for unusual or incorrect states. Python driver scripts should report progress with the project's existing `accelerate` logger or `tqdm` convention where available; confirm a suitable existing alternative for other stacks. This rule does not authorize installing either dependency.
- Do not create `README.md` files in subdirectories unless explicitly told to do so. Do not consider backward compatibility unless explicitly told to do so.
- Tests are allowed, including under `tests/`. Keep suites concise and focused on meaningful behavior and regressions. As development continues, consider suite growth and time and compute costs; consolidate or trim redundant or obsolete cases relevant to the current work while preserving meaningful coverage. Inspect affected tests and changes first, preserve unrelated and concurrent edits, and report material reductions. This permits scoped removal of redundant or obsolete test cases or files, not removal of useful coverage merely to obtain passing results or meet a budget. Report useful checks deferred by resource limits.
- Document confirmed lightweight test and check commands and their prerequisites. Run checks appropriate to the change within the authorized scope; report what was checked and any limitations. Do not claim unrun tests passed. Use "testing", "checks", or "verification" for software correctness to distinguish it from ML dataset terminology.
- After implementation and checks, if a concrete cleanup, organization improvement, fix, or modularization opportunity was encountered beyond the authorized test upkeep, propose it in one sentence in the conversation without executing it. Base it only on files already read; do not inspect unrelated files to find a suggestion.

**workflows/TASK_WORKFLOW.md**

- Ordinary code edits and initialization alone do not require a task ledger.
- If `workflows/TASKS.md` is absent when the user asks to create, track, or complete a task, create it. If it is absent for a condensation or compression request, report that there are no tasks to process. Preserve existing IDs and content except during explicitly requested condensation or historical compression; assign unused IDs for new entries.
- Use exactly two section headers in `workflows/TASKS.md`, in this order: `# History` and `# Current`. All other nonblank lines must be historical bullets or current checklist entries. Do not add a separate title, paragraphs, development notes, tables, or code blocks.
- In `History`, use a single tier of plain bullet points without checkboxes, each describing a completed outcome in one sentence.
- For detailed task entries in `Current`, use exactly two tiers of checkboxes. Outer items describe high-level tasks and start with IDs such as `T-01`; inner items describe one narrow local subtask per sentence and start with IDs such as `T-01.1`. An optional tag follows the ID.
- Write outer descriptions as concise, human-friendly, high-level Git commit subjects, using a direct action verb and familiar language; for example, "Add reusable figure-generation tools". Keep subtask descriptions sufficiently specific for an agent to execute and assess completion, without packing process notes into them.
- Agents may update descriptions without separate permission, but do so conservatively when facts, decisions, or the situation change. Preserve the agreed outcome and scope. Checking a box changes completion state only: do not rewrite present or imperative wording into past tense. Do not append caveats about unfinished work outside the stated task or add acceptance criteria merely to justify leaving it incomplete. Put actual blockers, checks performed or deferred, and follow-up context in relevant memory notes or the conversation. Historical summarization below remains a separate, explicitly requested operation.
- When a task is completed, check its boxes in-place. Keep the detailed entries available so the user can review or uncheck them. **Condense completed current tasks:** Only perform this function when the user explicitly asks to condense or compact completed current tasks or `workflows/TASKS.md`; then summarize each fully completed task as a one-sentence bullet in `History`, preserving task IDs and their relative order, broadly integrating the subtask outcomes, and removing those subtasks. Keep incomplete tasks under `Current`. This function does not merge existing historical entries.

  Simulated ML project ledger after an explicit compaction, with one completed outcome and an ongoing task:

  ```markdown
  # History

  - T-01 Added reproducible stratified training, development, and test splits with a fixed random seed.

  # Current

  - [ ] T-02 Add early stopping to model training.
    - [x] T-02.1 #code Add patience and minimum-improvement settings to the training configuration.
    - [x] T-02.2 #code Track the best loss on the development split and save its model weights in a separate checkpoint.
    - [ ] T-02.3 #test Check patience boundaries and best-weight restoration with a small synthetic training loop.
  ```

- **Compress historical tasks:** Only perform this function when the user explicitly asks to compress historical tasks. Group similar entries in `History` by shared feature, purpose, or outcome, and replace each group with fewer one-sentence historical task bullets. Retain higher-level accomplishments, significant decisions, and material outcomes while intentionally discarding low-level implementation steps and per-task granularity. Do not merge unrelated work or invent accomplishments; keep unmatched entries. Place each merged summary at the position of its earliest source entry, preserving the relative order of the remaining entries. If no entries can meaningfully be combined, report that and leave the ledger unchanged.
- After historical compression, update all task IDs in `workflows/TASKS.md`: renumber every top-level entry sequentially in document order, starting with `History` and continuing through `Current`; regenerate every current subtask ID from its new parent ID and sequential position. Update any references within `workflows/TASKS.md` and affected files under `workflows/memory/` to the corresponding new IDs, including references to source entries now represented by a merged summary. Preserve current task descriptions, tags, checkbox states, and subtask structure. Verify that IDs are unique, subtask IDs match their parents, and no stale references remain. Do not retain an old-ID mapping or write IDs outside `workflows/TASKS.md` and `workflows/memory/`.

- Mark work complete only when its stated outcome is achieved; do not check off blocked or merely proposed work.

**workflows/REVIEW_WORKFLOW.md**

- Be critical about design, implementation, organization, and correctness while respecting time and compute constraints.
- For scientific work, apply the scrutiny of a reviewer at a top-tier scientific conference. For other domains, adapt the review criteria to the intended users and project purpose.
- For every review point, whether the review was requested explicitly or implicitly, include three integer ratings from 1 to 5: **Priority** (urgency or significance of the problem), **Confidence** (certainty that the identified issue is valid), and **Effort** (amount of work needed to fix it). A rating of 5 means the highest urgency or significance, greatest certainty, or most work, respectively. Use explicit labels, for example: `Priority: 4/5; Confidence: 5/5; Effort: 2/5`.
- Report issues in descending priority. Tag each with an aspect such as `Code` or `ML design`. Explain the evidence, consequence, and a practical improvement; distinguish confirmed defects from open questions.
- Identify discrepancies among code, comments, documentation, and papers when those materials exist.

**workflows/PAPER_WORKFLOW.md**

- BibTeX management belongs to the user. Agents may read and use existing references for citations, but should request missing reference keys rather than invent or manage entries.
- Write clearly and naturally. Keep the introduction and abstract understandable to an undergraduate student, minimize unnecessary jargon, and avoid stock AI phrasing and em dashes.
- Put significant decisions that `probe-me` cannot settle, citation requests, or user work that takes time in `workflows/REQUESTS.md`. Use unique IDs and this format:

  ```markdown
  ## REQ-014 — Decision

  **Need:** Decide whether the paper claims scalability in vocabulary size or computational complexity.

  **Context:** The implementation removes the vocabulary-sized output layer, but temporal attention still scales with sequence length.

  ## REQ-015 — Citation

  **Need:** Find prior work supporting candidate-based prediction over large discrete spaces.

  **Claim:** Candidate-based prediction avoids a global vocabulary-sized output layer.
  ```

- Place a matching TODO comment, such as `%TODO REQ-014`, at the relevant `.tex` location. Adapt comment syntax for other confirmed authoring formats.
- When the user invokes the `decision` skill and the corresponding decision is found, or supplies the requested BibTeX key, apply the resolution and remove the resolved request and matching TODO. Preserve unrelated requests. Follow the actual skill instructions.

**workflows/MEMORY_WORKFLOW.md**

- Consult relevant existing notes before acting on resumed work; do not load unrelated notes merely because they exist.
- Save notes only in `workflows/memory/`, excluded from the parent project repository but tracked in the workflow repository. Verify the parent exclusion and independent workflow Git root before writing; do not exclude memory from the workflow repository. Create the directory only when needed. Use descriptive lowercase hyphenated topic or feature filenames, such as `drawio-figure-export.md`, so an agent can infer relevance from `ls` alone; avoid generic names such as `notes.md` or date-only names. Task IDs are allowed in note contents; keep them aligned with `workflows/TASKS.md`. Update relevant notes rather than duplicating them.
- Memory is agent-initiated record keeping and provisional working choices: current state, relevant paths, blockers, checks performed or deferred, and next steps. Human-initiated decisions are permanent instructions until the user changes them. Do not override, silently promote, or retire decisions through memory maintenance; follow the decision skill for explicit requests to persist or change policy.
- Keep memory fluid rather than append-only. For the work being handled, use recency, priority, and frequency of reuse to retain useful context, merge repetition, shorten stale detail, and remove obsolete notes. Preserve active blockers and important unresolved context even when old. Do not perform whole-store sweeps or treat age alone as grounds for deletion.
- Keep human-facing documentation in `docs/` or established equivalents accurate, readable, and focused on high-level ideas and usage. Agent implementation details, process history, and resume instructions belong in memory, not human documentation. Avoid transcripts and running diaries.
- This workflow authorizes narrowly scoped removal of obsolete notes within `workflows/memory/`, including tracked notes; inspect their workflow Git changes first and preserve unrelated notes and user or other-agent changes. Leave staging and commits to the user; synchronization remains subject to confirmed authorization.

**workflows/TOOLS_WORKFLOW.md**

- Before creating a helper, inspect `workflows/tools/TOOL_MAP.json` if present and read relevant tools; reuse or adapt a suitable tool rather than creating duplicates.
- Store helpers in `workflows/tools/` only when future reuse is plausible. They must be outside the main project's implementation and human workflows: project code, builds, tests, and human-facing commands must not depend on them. Helpers may read project-specific inputs and generate requested project artifacts. An agent-only Draw.io XML generator qualifies; an application module or human-facing CLI does not.
- Create the directory and `TOOL_MAP.json` only when retaining the first qualifying tool. Use descriptive script names and keep the map a JSON object from script paths relative to `workflows/tools/` to brief, specific purpose strings, for example `{"drawio_xml.py": "Generate Draw.io figures from node and edge specifications."}`. Maintain one entry per reusable helper entry point, no stale paths, and no inventories of generated artifacts or unnecessary metadata.
- Keep scripts and any usage comments concise, with enough information for another agent to reuse them. Update the map together with tool additions or authorized changes. Parse the JSON and check that each mapped entry point exists and each retained helper entry point is mapped. Test new or changed behavior with a small relevant check when feasible within existing execution limits.
- Keep helpers and the map eligible for tracking in workflow Git, excluded from the main repository; leave staging and commits to the user. Keep generated outputs in authorized artifact locations, separate from reusable scripts. Retaining a tool does not authorize new dependencies, environment changes, expensive runs, artifact overwrites, or unrelated tool cleanup.
